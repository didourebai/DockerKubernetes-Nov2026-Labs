Avant de commencer

Utiliser un cluster Kubernetes local opérationnel (par exemple Docker Desktop), avec kubectl et un accès aux images publiques. Les commandes suivantes sont prévues pour PowerShell. Les démos 3 et 4 réutilisent le Deployment web de la démo 1.

Attention : vérifier le contexte avant toute manipulation. Ne pas utiliser un cluster de production. Créer un namespace neuf réservé à cet atelier ; si le nom existe déjà, choisir un autre nom et adapter les commandes.

kubectl config current-context
kubectl get nodes
kubectl create namespace atelier-k8s
kubectl config set-context --current --namespace=atelier-k8s

Noter le namespace initial pour le restaurer après l’atelier. Les commandes supposent que le namespace courant est bien atelier-k8s.

DÉMO 01 · 15 min · Deployment · ReplicaSet · Pod

Réconciliation automatique

Comprendre comment Kubernetes maintient l’état souhaité.

1. Créer trois réplicas

kubectl create deployment web --image=nginx --replicas=3
kubectl rollout status deployment/web
kubectl get deployments
kubectl get replicasets
kubectl get pods
À observer : Trois Pods disponibles, un Deployment et un ReplicaSet.

2. Observer puis supprimer un Pod

kubectl get pods -w
À observer : Dans un deuxième terminal, exécuter la commande suivante.

3. Supprimer un Pod

kubectl delete pod NOM_DU_POD
À observer : Remplacer NOM_DU_POD par un nom réel. Un nouveau Pod apparaît automatiquement ; son nom et éventuellement son IP changent.

4. Changer le nombre de réplicas

kubectl scale deployment web --replicas=5
kubectl rollout status deployment/web
kubectl get pods
kubectl scale deployment web --replicas=3
kubectl rollout status deployment/web
À observer : Le nombre de Pods passe à cinq puis revient à trois.
Question aux participants

Si je supprime un Pod, combien de Pods restera-t-il après stabilisation ?

Dévoiler la réponse et l’explication orale

Trois. Le ReplicaSet compare l’état réel à l’état souhaité et crée un remplacement. Le Deployment pilote le ReplicaSet. Le Scheduler choisit un nœud pour le nouveau Pod ; le kubelet y fait démarrer le conteneur. Le scaling horizontal modifie le nombre de réplicas, pas la puissance de chaque conteneur.

DÉMO 02 · 15 min · ErrImagePull · ImagePullBackOff · Events

Diagnostiquer une image invalide

Identifier à quelle étape du cycle de vie survient une erreur.

1. Provoquer une erreur

kubectl create deployment web-erreur --image=nginx:version-inexistante
kubectl get pods -l app=web-erreur
À observer : Après un délai, ErrImagePull ou ImagePullBackOff apparaît.

2. Examiner les événements

kubectl describe pod -l app=web-erreur
kubectl get events --sort-by=.lastTimestamp
À observer : Chercher les messages Failed et BackOff relatifs au téléchargement de l’image.

3. Corriger le Deployment

kubectl set image deployment/web-erreur nginx=nginx:latest
kubectl rollout status deployment/web-erreur
kubectl get pods -l app=web-erreur
À observer : Le nouveau Pod devient Running et Ready si le registre est accessible.
Question aux participants

Pourquoi kubectl logs ne suffit-il pas dans ce scénario ?

Dévoiler la réponse et l’explication orale

Le conteneur n’a pas encore démarré : il ne produit donc pas de journaux applicatifs. Les événements permettent de diagnostiquer un tag absent, un problème réseau ou une authentification manquante. Le statut ImagePullBackOff indique que Kubernetes espace les tentatives.

DÉMO 03 · 20 min · Service · Labels · EndpointSlices

Service inaccessible malgré des Pods Running

Comprendre la sélection des destinations réseau.

1. Créer un Service

kubectl expose deployment web --port=80 --target-port=80
kubectl get services
kubectl get pods -l app=web --show-labels
kubectl describe service web
kubectl get endpointslices -l kubernetes.io/service-name=web
À observer : Le Service sélectionne les Pods portant app=web.

2. Tester depuis le navigateur

kubectl port-forward service/web 8080:80
À observer : Ouvrir http://localhost:8080. Arrêter le port-forward avec Ctrl+C avant la suite.

3. Introduire un mauvais sélecteur

kubectl set selector service web app=inexistant
kubectl get pods -l app=web
kubectl describe service web
kubectl get endpointslices -l kubernetes.io/service-name=web
kubectl get endpointslices -l kubernetes.io/service-name=web -o yaml
À observer : Les Pods restent Running, mais le Service ne dispose plus de destination correspondante. Attendre la réconciliation si nécessaire.

4. Tester depuis le réseau du cluster

kubectl run test-http --image=busybox:1.36 --restart=Never --rm -i -- wget -T 5 -qO- http://web
À observer : Le test doit échouer avec le mauvais sélecteur. Le téléchargement initial de BusyBox nécessite un accès au registre.

5. Rétablir le sélecteur

kubectl set selector service web app=web
kubectl get endpointslices -l kubernetes.io/service-name=web
kubectl run test-http-ok --image=busybox:1.36 --restart=Never --rm -i -- wget -T 5 -qO- http://web
À observer : Une réponse HTML de NGINX est attendue après mise à jour des EndpointSlices.
Question aux participants

Pourquoi le Service est-il inaccessible alors que les Pods fonctionnent ?

Dévoiler la réponse et l’explication orale

Le Service utilise un sélecteur de labels et non les noms des Pods. Si aucun Pod ne correspond, aucune destination utilisable n’est disponible. Le port-forward est un accès de diagnostic à un Pod sélectionné, et non une preuve du chemin réseau normal du Service ; le test BusyBox vérifie aussi le DNS et le trafic interne.

DÉMO 04 · 15 min · Rolling Update · Rollout · Révisions

Mise à jour échouée et rollback

Comprendre comment revenir à une configuration précédente.

1. Vérifier la version stable

kubectl scale deployment web --replicas=3
kubectl rollout status deployment/web
kubectl get pods -l app=web
À observer : Trois Pods disponibles avant la mise à jour.

2. Déployer une image invalide

kubectl set image deployment/web nginx=nginx:version-inexistante
kubectl get pods -l app=web
kubectl get replicasets -l app=web
kubectl rollout history deployment/web
À observer : Un nouveau ReplicaSet apparaît. Les nouveaux Pods échouent à récupérer l’image.

3. Examiner le blocage

kubectl describe deployment web
kubectl rollout status deployment/web --timeout=20s
À observer : Le rollout ne se termine pas. Avec les paramètres RollingUpdate par défaut et trois réplicas, les anciennes instances disponibles sont normalement conservées.

4. Revenir en arrière

kubectl rollout undo deployment/web
kubectl rollout status deployment/web
kubectl get pods -l app=web
À observer : Le Deployment revient à son modèle de Pod précédent et retrouve ses réplicas disponibles.
Question aux participants

Les anciens Pods sont-ils forcément supprimés avant que les nouveaux soient prêts ?

Dévoiler la réponse et l’explication orale

Non. maxSurge contrôle le surplus de Pods autorisé et maxUnavailable le nombre de réplicas pouvant être indisponibles. Avec trois réplicas et les valeurs par défaut de 25 %, cela donne généralement un Pod supplémentaire et zéro indisponibilité autorisée. Le rollback restaure le modèle de Pod, pas les données ni les migrations de base de données.

DÉMO 05 · 15 min · Scheduler · Requests · Limits · FinOps

Pod bloqué en Pending

Comprendre le placement et le dimensionnement des ressources.

1. Examiner la capacité du cluster

kubectl get nodes
kubectl describe nodes
À observer : Observer la capacité allocatable. La demande suivante suppose un cluster dont aucun nœud ne peut fournir 100 CPU.

2. Créer pod-resources.yaml (version invalide pour un petit cluster)

apiVersion: v1
kind: Pod
metadata:
  name: demo-resources
spec:
  containers:
    - name: nginx
      image: nginx
      resources:
        requests:
          cpu: "100"
          memory: "128Mi"
À observer : Enregistrer ce YAML dans pod-resources.yaml.

3. Observer le placement

kubectl apply -f pod-resources.yaml
kubectl get pod demo-resources
kubectl describe pod demo-resources
À observer : Le Pod reste Pending ; chercher FailedScheduling et Insufficient cpu.

4. Remplacer le fichier par cette version

apiVersion: v1
kind: Pod
metadata:
  name: demo-resources
spec:
  containers:
    - name: nginx
      image: nginx
      resources:
        requests:
          cpu: "100m"
          memory: "128Mi"
        limits:
          cpu: "200m"
          memory: "256Mi"
À observer : 100m correspond à 0,1 CPU. Les limites encadrent la consommation.

5. Recréer le Pod

kubectl delete pod demo-resources
kubectl apply -f pod-resources.yaml
kubectl get pod demo-resources -w
À observer : Le Pod peut être placé si le cluster dispose des ressources nécessaires. Ctrl+C pour quitter la surveillance.
Question aux participants

Est-ce un problème d’image, de réseau ou de capacité ?

Dévoiler la réponse et l’explication orale

C’est un problème de placement. Le Scheduler compare les requests aux ressources disponibles sur les nœuds. Une limite CPU peut entraîner du throttling ; dépasser la limite mémoire peut entraîner un OOMKilled. Des requests trop élevées peuvent provoquer du surdimensionnement et augmenter les coûts : c’est un lien concret avec FinOps.

Nettoyage

Supprimer uniquement les ressources de cet atelier. Si le namespace a été créé exclusivement pour cette démo, le supprimer après avoir restauré le namespace initial (ici default, à adapter).

kubectl config set-context --current --namespace=default
kubectl delete namespace atelier-k8s

La suppression du namespace efface toutes ses ressources. Vérifier qu’il ne contient rien à conserver.
